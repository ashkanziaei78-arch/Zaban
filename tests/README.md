# آزمون‌های تاکورا

آزمون‌هایی که پیش از هر انتشار باید سبز باشند. بیشترشان به
یک MySQL/MariaDB واقعی نیاز دارند — نه به سرور زنده، بلکه به یک نمونهٔ
موقت که چند دقیقه بالا می‌آید و دور انداخته می‌شود.

## چرا با دیتابیس واقعی

اسکیمای نسخهٔ ۶ دو تضمین امنیتی دارد که **فقط** در سطح دیتابیس اعمال
می‌شوند: یگانگی مالک پلتفرم، و دیوار مجوزهای سطح پلتفرم. هیچ آزمون
ایستایی نمی‌تواند ثابت کند این دو واقعاً کار می‌کنند؛ باید تلاش کرد
نقضشان کرد و دید که دیتابیس رد می‌کند.

## راه‌اندازی نمونهٔ موقت

```bash
mariadb-install-db --datadir=/tmp/tk-test/data --password="" --port=3399
mariadbd --defaults-file=/tmp/tk-test/data/my.ini --port=3399 --console &
```

اگر پورت یا مسیر دیگری خواستید:

```bash
export TALKORA_TEST_DSN="mysql:host=127.0.0.1;port=3399;charset=utf8mb4"
export TALKORA_TEST_DSN_DB="mysql:host=127.0.0.1;port=3399;dbname=talkora_test;charset=utf8mb4"
```

PHP باید `pdo_mysql` داشته باشد.

## اجرا

```bash
python tests/membership-role-id.py   # دیتابیس نمی‌خواهد، اول و ارزان
python tests/schema-drift.py         # دو پایگاه موقت می‌سازد و دور می‌اندازد

php tests/schema.php                 # دیتابیس آزمون را از نو می‌سازد
php tests/equivalence.php            # روی همان دیتابیس
php tests/multirole.php
php tests/demo-lifecycle.php

# این دو سرور PHP می‌خواهند:
#   php -S 127.0.0.1:8099 -t panel
python tests/signup.py
python tests/joinflow.py
python tests/notify.py
python tests/classdates.py

# آزمون اعلانِ پلتفرم سرور سوپرادمین هم می‌خواهد:
#   cp panel/api/config.php superadmin/api/config.php
#   php -S 127.0.0.1:8101 -t superadmin
python tests/notify-platform.py

# وبلاگ سرور سایت را هم می‌خواهد. site/api/ در مخزن نیست چون
# build-dist.py خودش از panel/api/ می‌سازدش؛ برای آزمون محلی:
#   mkdir -p site/api
#   cp panel/api/{_bootstrap,_settings,public,config}.php site/api/
#   php -S 127.0.0.1:8102 -t site
python tests/blog.py
```

آزمون‌های HTTP که ثبت‌نامِ مدیر می‌سازند به سقف نرخ می‌خورند (۱۵ در
ساعت روی هر IP). برای اجرای پشت‌سرهم:

```sql
DELETE FROM rate_limit;
```

`schema.php` سوپرادمینی با نام `owner` و رمز `admin12345` می‌سازد که
`notify-platform.py` با آن وارد می‌شود.

ترتیب مهم است: `schema.php` دیتابیس را از نو می‌سازد، پس هرچه بعدش
می‌آید روی همان ساختار تازه کار می‌کند. همه با کد خروج غیرصفر شکست
می‌خورند، پس در اسکریپت هم قابل استفاده‌اند.

### `schema.php` — ۲۵ بررسی

اسکیما را با **همان منطق تکه‌کردنی** اجرا می‌کند که `install.php` دارد
(تقسیم روی نقطه‌ویرگول، حذف خطوط توضیح). اگر دستوری زیر آن تقسیم بشکند،
اینجا معلوم می‌شود نه روی سرور مشتری.

بعد تلاش می‌کند تضمین‌ها را نقض کند و انتظار دارد رد شود:

- ساخت مالک پلتفرم دوم
- ارتقای یک ادمین عادی به مالک
- چسباندن مجوز سطح پلتفرم به یک نقش
- دور زدن همان با `is_platform=1`
- اعطای مجوز سطح پلتفرم به یک کاربر
- مقدار نامعتبر برای `effect`

### `equivalence.php` — ۸۱ مقایسه

برای هر یک از ۲۷ نقطهٔ بررسی دسترسی و هر سه نقش سیستمی، تصمیم پیش از
مهاجرت (`require_role`) و پس از آن (`require_perm`) را کنار هم می‌گذارد.

هدف این نیست که همه یکسان باشند — شش تفاوت عمدی است و در سند معماری
خواسته شده. هدف این است که **هیچ تفاوتی ناخواسته نماند**: هر تفاوت باید
در فهرست `EXPECTED_DIFFS` با دلیلش باشد، وگرنه آزمون می‌شکند.

همین آزمون در فاز ۳ یک رگرسیون امنیتی واقعی گرفت: زبان‌آموز مجوز
`attendance.view` را دارد (با محدودهٔ خودش)، پس `require_perm` تنهایی
پاس می‌شد و می‌توانست تاریخچهٔ حضور زبان‌آموز دیگری را ببیند. نتیجه‌اش
تابع `require_perm_on_user()` شد که محدوده را هم اعمال می‌کند.

### `multirole.php` — ۱۱ بررسی

قید سه‌تایی عضویت: یک نفر می‌تواند در یک آموزشگاه هم مدیر باشد هم
مدرس، ولی دو عضویتِ هم‌نقش هنوز رد می‌شود. همچنین کلید خارجی نقش و
عضویت زمان‌دار.

### `demo-lifecycle.php` — ۱۹ بررسی

چرخهٔ دموی زمان‌دار: تأیید، تمدید، تبدیل به مشتری، و جاروی
عضویت‌های منقضی.

### `signup.py` — ۲۱ بررسی

هر سه مسیر ثبت‌نام از راه HTTP واقعی: ساخت آموزشگاه، کد پیوستن، صف
درخواست. اعتبارسنجی کد ملی و تاریخ تولد، و اینکه فهرست عمومی
آموزشگاه‌ها چیزی جز نام و شهر نشت نمی‌دهد.

هر اجرا شمارهٔ موبایل و کد ملیِ معتبرِ تازه می‌سازد. نسخهٔ اول کد ملی
ثابت داشت و فقط یک‌بار سبز می‌شد؛ آزمونی که دومین بار قرمز می‌شود،
دیگر اجرا نمی‌شود.

### `joinflow.py` — ۲۴ بررسی

چرخهٔ پیوستن از هر دو سر: مدیر کد صادر می‌کند، کسی با کد عضو می‌شود،
کد چرخانده می‌شود و کد قبلی می‌سوزد، کس دیگری در صف می‌نشیند و مدیر
تأیید یا ردش می‌کند.

دو نکته را جدا می‌آزماید: نقشِ مدیر بر خواستهٔ متقاضی مقدم است — وگرنه
هرکس با زدن «مدرس» در فرم ثبت‌نام، با یک کلیک مدیر دسترسی مدرس
می‌گرفت — و زبان‌آموزِ همان آموزشگاه نه صف را می‌بیند نه کد صادر
می‌کند.

`signup.py` فقط سمت متقاضی را می‌دید و درخواست را تا صف دنبال می‌کرد.
تا پیش از این آزمون، آن صف چاه بی‌ته بود.

### `notify.py` — ۴۰ بررسی

اعلان تنها جایی است که یک کاربر مستقیماً به صندوق کاربر دیگری
می‌نویسد، پس بیشترِ این آزمون دربارهٔ محدوده است نه ویژگی:

- مدرس نه «همهٔ آموزشگاه» را در فهرست مخاطبان می‌بیند نه «همهٔ
  زبان‌آموزان»، و اگر کلیدشان را دستی بفرستد ۴۰۳ می‌گیرد
- مدرس کلاسِ همکارش را نه می‌بیند نه به آن می‌فرستد، و زبان‌آموزِ آن
  کلاس چیزی نمی‌گیرد
- زبان‌آموز اصلاً نمی‌فرستد و فهرست مخاطبان را نمی‌بیند
- کسی نمی‌تواند اعلانِ دیگری را «خوانده» اعلام کند

و یک بررسی که ویژگی نیست، صداقت است: پیامک هنوز قالب مصوب sms.ir
برای متن آزاد ندارد، پس درخواستش رد می‌شود و `sms_sent` صفر می‌ماند —
به‌جای اینکه یک ستون بگوید پیامکی رفته که نرفته.

### `classdates.py` — ۳۷ بررسی

فاز ج: تاریخ‌های کلاس، تمدید مهلت تکلیف، شمار غیبت.

بیشترِ آزمون روی *ترتیب* تاریخ‌هاست نه وجودشان — پایان پیش از شروع،
میان‌ترم پیش از شروع، پایان‌ترم بعد از پایان کلاس. هر کدام خطای تایپی
است و اگر همان‌جا گرفته نشود، بعداً به شکل «۰ جلسه مانده» یا کارنامهٔ
وارونه بیرون می‌زند و کسی نمی‌فهمد از کجا آمده.

یک بررسی جدا برای تفاوتِ «کلید نفرستاده‌شده» و «کلید خالی»: اولی یعنی
دست نزن، دومی یعنی پاک کن. بدون این تفکیک، هر ذخیرهٔ جزئی — عوض‌کردن
ظرفیت — همهٔ تاریخ‌ها را می‌شست.

تمدید مهلت: تمدید به عقب رد می‌شود (جلو کشیدن است، نه تمدید)، مهلت
اصلی دست‌نخورده می‌ماند، و تحویل‌هایی که فقط به‌خاطر مهلت قدیمی «دیر»
بودند دیگر دیر نیستند.

### `notify-platform.py` — ۳۰ بررسی

اعلان سوپرادمین تنها جای سامانه است که عمداً از مرز چند-مستأجری رد
می‌شود، پس بیشتر این آزمون همان مرز را می‌سنجد:

- اعلان به «همهٔ مدیران» به مدیرِ هر دو آموزشگاه می‌رسد و به هیچ
  زبان‌آموزی نه
- اعلانِ یک آموزشگاه فقط به اعضای همان می‌رسد
- اعلان پلتفرم — حتی وقتی به یک آموزشگاه رفته — در فهرست «فرستاده‌های»
  مدیر آن آموزشگاه نیست؛ آن فهرست «چیزهایی که *ما* فرستادیم» است

سقف ۵۰۰۰ گیرنده هم عمدی است: فرستادن به ده‌هزار نفر یعنی ده‌هزار ردیف
در یک تراکنش، که روی هاست اشتراکی می‌شود timeout و تراکنشِ نیمه‌کاره.

### `blog.py` — ۶۰ بررسی

بیشترش دربارهٔ پالایش HTML است. نویسنده سوپرادمین است و به او اعتماد
داریم — ولی اعتماد به آدم، اعتماد به مرورگرِ اوست: متنی که از Word
کپی شده صد تگ اضافه دارد، و اگر روزی حسابی لو برود، اسکریپت
ذخیره‌شده به *همهٔ* بازدیدکننده‌ها می‌رسد نه فقط به مهاجم.

بخش «دور زدن اسکیم» نُه حالت را می‌سنجد، از `javascript:` ساده تا
`java<tab>script:` که مرورگر اجرایش می‌کند. و سه حالتِ سالم که
*نباید* حذف شوند — یک بار `uploads/x.png`، ساده‌ترین مسیر نسبی
ممکن، قربانی سخت‌گیری شد و تصویرِ خودِ وبلاگ حذف می‌شد.

بقیه دربارهٔ سئوست و همه سمت سرور بررسی می‌شود، چون تمام نکته همین
است: عنوان و متن و JSON-LD باید در خودِ HTML باشند، نه از راه
جاوااسکریپت. پیش‌نویس ۴۰۴ می‌دهد نه ۲۰۰-با-پیام (که «soft 404» است و
کل سایت را کم‌کیفیت‌تر نشان می‌دهد).

### `membership-role-id.py` — ایستا، بدون دیتابیس

هیچ `INSERT INTO membership` نباید `role_id` را جا بیندازد.

از مهاجرت ۰۰۶ این ستون ناتهی است و عمداً پیش‌فرض ندارد — پیش‌فرض یعنی
عضویتی که ستونش جا افتاده، بی‌صدا مجوزهای نقش دیگری بگیرد. ولی شش
دستور در کد آن را ننوشته بودند و روی MySQL با `STRICT_TRANS_TABLES`
خطا می‌دادند: دعوت عضو، ورود با پیامک (هر دو مسیرش)، ساخت فضای کاری و
دو دستور سوپرادمین. یعنی از لحظهٔ اجرای ۰۰۶ روی سرور زنده، هیچ عضو
تازه‌ای اضافه نمی‌شد.

### `schema-drift.py` — نصب تازه در برابر مهاجرت‌ها

مخزن دو مسیر به یک ساختار دارد: `panel/api/schema.mysql.sql` برای نصب
تازه، و `migrations/*.sql` برای سرورهای موجود. هر تغییر باید در هر دو
بنشیند.

آزمون هر دو مسیر را روی دو پایگاه خالی می‌سازد و ستون، ایندکس و قید را
مقایسه می‌کند. قیدها جدا خوانده می‌شوند چون کلید خارجی روی ستونی که از
قبل ایندکس دارد، ایندکس تازه نمی‌سازد و از دید ایندکس‌ها پنهان می‌ماند.

این رانش دو بار افتاد: یک‌بار `institute.status` که مهاجرت ۰۰۸ ترمیمش
کرد، و یک‌بار مهاجرت‌های ۰۰۷ و ۰۰۹ که اصلاً به فایل پایه نرسیدند —
نصب تازه `membership.role_id` نداشت، پس هیچ عضوی ساخته نمی‌شد.

## بررسی سوم

`build-dist.py` هم یک بررسی یکپارچگی دارد که به دیتابیس نیاز ندارد:
کلید مجوز تایپی، نقش ناموجود، محدودهٔ ناشناخته، و مجوز پلتفرمی چسبیده
به نقش را می‌گیرد و ساخت را متوقف می‌کند.

```bash
python3 build-dist.py
```
